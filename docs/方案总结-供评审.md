# 本地数字人直播应用：方案总结（供外部评审）

本文是自包含的，评审者不需要读其他文件。文中的数字都是实测值，测试机与目标机不同，凡是折算的地方都有标注。写作日期 2026-11-25，项目处于原型验证阶段。

## 1. 要做什么

一个 Windows 桌面应用，面向没有技术背景的普通主播：

- 主播提供自己的真人视频和一小段声音。
- 开播后，软件读取直播间弹幕，用本地大模型生成回复，用主播的音色说出来，并驱动视频里的人对上口型。
- 画面和声音送进本机的"抖音直播伴侣"推流。
- 全部在本机运行，不调用云端接口。

## 2. 硬性约束

| 约束 | 说明 |
|---|---|
| 目标硬件 | RTX 3060 12G 显存，家用 CPU，16 到 32G 内存 |
| 全本地 | 模型推理不联网 |
| 实时互动 | 弹幕是直播间实时产生的，不能预先生成回复。从弹幕出现到数字人开口，目标 3 到 5 秒以内；开口后必须连续播放不中断 |
| 语音有表现力 | 语气和情绪要自然，不接受为了速度换成平淡的语音。这一条不能妥协 |
| 画面不穿帮 | 嘴部周围不能有明显的模糊，观众不能一眼看出是合成的 |
| 普通主播能用 | 一键安装，自动适配，界面不出现技术名词 |
| 可商用许可 | 模型和权重的许可证需要允许商用 |

暂不考虑：弹幕如何从抖音直播间采集（测试阶段从文件读取，按"逐条实时到达"的方式运行和计量）。

## 3. 当前架构

```
弹幕 -> 大模型(流式) -> 切句 -> 语音合成 -> 口型驱动 -> 贴回原图 -> 编码/播放 -> 直播伴侣
                                                 ^
                                  人物视频(预处理后的底板帧；不说话时循环播放作待机画面)
```

进程划分：

| 进程 | 内容 |
|---|---|
| llama-server（外部进程） | 大模型，本机 HTTP 接口，流式输出 |
| 语音合成进程 | 独立 Python 进程。和口型放在同一进程时会争抢解释器锁，实测两者都慢约一倍，所以拆开 |
| 主进程 | 口型的显卡推理（主线程）、大模型流式读取与切句（线程）、贴图与视频编码（线程） |

流式处理的要点：大模型凑够一句就立刻送去合成；每条回复的第一段遇到逗号就提前切出，让数字人更早开口；模型加载时用假数据预热，避免第一句话卡顿。

## 4. 选型与理由

| 环节 | 当前选型 | 理由 | 已知问题 |
|---|---|---|---|
| 大模型 | Qwen3-4B，Q4_K_M 量化（GGUF），llama.cpp CUDA 版，上下文 2048，关闭思考模式 | 中文好，回复只有两三句，4B 足够；速度远超需要 | 无 |
| 语音合成（声音克隆） | GPT-SoVITS v2ProPlus，半精度，零样本克隆（6.8 秒参考音频加文本） | 显存小，Windows 支持成熟，MIT 许可 | 是当前的速度瓶颈；表现力依赖参考音频 |
| 口型驱动 | MuseTalk 1.5，半精度，批大小 8，torch.compile | 单步推理，能实时；MIT 许可 | 输出只有 256x256，贴回大脸时模糊；权重训练用了 HDTF 数据集，官方提示商用需与数据集所有方沟通 |
| 送入直播伴侣 | 计划：无边框播放窗口加直播伴侣的"窗口捕获"和桌面音频 | 不需要装虚拟摄像头驱动 | 尚未实现，目前只输出 mp4 文件 |
| 界面 | 计划：PySide6 | 与模型同语言，打包简单 | 尚未实现 |

评估过但没有采用的：

| 候选 | 结论 |
|---|---|
| Kokoro-82M 中文版（预置音色，不克隆） | 极快（首句 0.3 秒，整体生成耗时比 0.40，显存少 2G），但小模型表现力不足，不满足"语音有表现力"的约束，只留作测速参照 |
| CosyVoice 3（Fun-CosyVoice3-0.5B） | 支持情绪指令和流式输出，理论上最符合表现力要求。但在 Windows 上按默认方式运行，生成耗时是音频时长的 1.4 到 1.5 倍，首段出声要 7 秒左右，显存 3.8G。未做 TensorRT 等加速，也未缓存说话人特征，优化空间未知 |
| llama.cpp Vulkan 版 | 单独运行与 CUDA 版相近（184 对 192 词元/秒），并发时更慢（86 对 109），只在体积上有优势，未采用 |

## 5. 实测数据

测试机：RTX 3080 Ti 12G，Xeon Gold 6248 2.5GHz 6 核，Windows Server 2022。**不是目标机**。3060 的显卡算力约为 3080 Ti 的 0.6 倍；测试机的 CPU 单核偏慢，而语音合成很依赖 CPU 单核，所以折算到目标机的数字不可靠，尚无 3060 实机数据。

### 5.1 单模块

| 模块 | 速度 | 显存 |
|---|---|---|
| 大模型 | 192 词元/秒，单次回复约 0.2 秒 | 进程约 3.3G |
| GPT-SoVITS | 生成耗时为音频时长的 0.36 到 0.54 倍，因音色和句长而异 | 进程约 3.2G |
| MuseTalk | 显卡部分约 18 到 23 毫秒/帧（UNet 约 7，VAE 解码约 11 到 16） | 进程约 3.3G（只做口型时的整机占用） |

口型每帧耗时的大头是 VAE 解码。只升级 PyTorch、channels_last、cudnn.benchmark 都无效；torch.compile 把 VAE 解码从 15.7 毫秒降到 10.7 毫秒。TensorRT 未测。贴回原图的官方实现要 25 毫秒/帧，重写为只处理人脸区域后约 7.5 毫秒，输出逐像素一致。

### 5.2 端到端（5 条弹幕逐条到达，输出 25 fps 竖屏视频）

"生成耗时比"指生成耗时除以视频时长，小于 1 才能边生成边播。

| 配置 | 平均首帧延迟 | 生成耗时比 | 显存峰值 |
|---|---|---|---|
| 三环节串行 | 未测 | 1.50 | 9.0G |
| 同进程多线程并行 | 未测 | 1.03 | 9.1G |
| 语音独立进程加流式，示例素材 | 2.4 秒 | 0.82 | 9.4G |
| 同上，改用真实中文素材 | 2.3 到 2.4 秒 | 1.10 到 1.12 | 9.4G |
| 预置音色 Kokoro（参照） | 0.5 秒 | 0.40 | 7.5G |
| 只做口型，语音预先生成（参照） | 不适用 | 0.42 | 3.3G |

说明：

- 延迟几乎全部花在第一句语音的合成上（约 2 秒）；大模型出第一句只要 0.1 到 0.2 秒，口型再加约 0.2 秒。
- 真实中文素材的那两次测试期间，后台有安装和下载任务占用 CPU，数字偏悲观，尚未在干净环境下重测。
- 语音合成的参数在单独测试时有明显差异（关闭并行推理后单句从 2.0 秒降到 1.3 秒），放进完整流程后只改善约 0.2 秒，原因是多个进程同时占用显卡。

## 6. 尚未解决的问题

按严重程度排序。

**问题一：声音克隆的速度不够，目标机上做不到持续实时。**
生成耗时比在测试机上是 0.8 到 1.1，折算到 3060 大于 1。口型部分单独看有余量（0.42），瓶颈在语音合成，以及语音与口型同时占用显卡时的互相拖累。

**问题二：嘴部周围模糊，观众能看出来。**
MuseTalk 输出 256x256，测试视频里人脸约 350x480 像素，贴回时要放大 1.4 到 2 倍。已做的缓解：融合范围收窄到嘴和下巴、Lanczos 放大、锐化，下半脸清晰度从原画面的 62% 提到 86%，但嘴唇边缘和口腔内部仍然偏软。未做：人脸修复模型（GFPGAN、CodeFormer）、更高分辨率的口型模型。

**问题三：表现力与速度的矛盾。**
有表现力的引擎（GPT-SoVITS、CosyVoice 3）慢，快的引擎（Kokoro）表现力不够。CosyVoice 3 的表现力可能更好，但目前比实时还慢。两个引擎的试听对比已生成，尚未做主观评价。

**问题四：显存余量小。**
三个模型同时运行峰值 9.4G。早期一次测试中显存溢出到系统内存，一句话的合成从 4 秒变成 206 秒。如果再加人脸修复模型，会更紧。

**问题五：没有在目标硬件上验证过。**
所有数字来自 3080 Ti。

**其他未完成的部分：** 实时播放与送入直播伴侣、桌面界面、多段视频之间的平滑切换（计划用姿态匹配找切换点加 RIFE 插帧）、弹幕筛选与排队、安装包、模型启动时间（目前 45 到 100 秒，主要是 torch.compile 的编译）。

## 7. 希望评审回答的问题

1. **总体可行性**：在 RTX 3060 12G 上同时满足"实时、有表现力的克隆语音、嘴部清晰"，这个目标现实吗？如果必须放宽一项，放宽哪一项代价最小？
2. **语音合成**：有没有既有表现力、支持中文声音克隆、又能在 3060 上与口型模型共存并明显快于实时的开源方案？GPT-SoVITS 和 CosyVoice 3 各自还有哪些我们没用上的加速手段（TensorRT、ONNX、说话人特征缓存、流式分块、蒸馏或更小的变体）？
3. **口型清晰度**：在保持实时的前提下，怎样解决 256x256 输出放大后的模糊？人脸修复模型的每帧开销在 3060 上是否承受得起？有没有分辨率更高且能实时的口型模型？
4. **显卡调度**：语音合成和口型驱动在两个进程里同时占用一张显卡，互相拖慢。应该错开执行、合并到一个进程用别的方式规避解释器锁，还是有更好的做法？
5. **架构**：现在的进程划分和流式流程有没有明显的设计缺陷？有没有更简单的整体结构？
6. **把一部分计算放到 CPU**：大模型或语音合成的某些阶段放到 CPU 上运行，是否能缓解显卡争抢并改善整体吞吐？
7. **许可风险**：MuseTalk 权重涉及 HDTF 数据集，商用是否构成实质风险？有没有许可更干净的替代品？
8. **我们遗漏了什么**：有没有这类产品常见、而本文完全没有提到的问题？
