# 本地数字人直播应用：技术方案与选型

## Context

目标：做一个全本地运行的 Windows 桌面应用。输入是若干人物视频和直播间的弹幕，应用用本地大模型生成回复、用克隆音色合成语音、实时驱动人物口型，把画面和声音送进本机的抖音直播伴侣开播。最终要能在 RTX 3060 12G 上运行，并以一键安装包形式交付。

已确认的需求：

- 弹幕来源：正式运行时来自直播间，实时产生、无法预知；预先给定的弹幕文件只用于测试（2026-11-25 澄清，最初的方案误把它当成了正式输入方式）。
- 数字人形态：以人物视频为底板，实时口型驱动。
- 内容与声音：本地 LLM 生成回复；音色既支持克隆（视频中人物或用户上传的音频），也提供预置音色供直接选用。
- 交付：带界面的桌面应用，一键安装。

现状：本地项目目录 `E:\AIAgent\ai_live_desktop` 为空，属于全新项目。开发机是 Windows Server 2022，RTX 3080 Ti 12G，32G 内存，C 盘剩余约 65G，只装了 NVIDIA 驱动，没有 Python、git、ffmpeg。

## 实时性要求

正式运行时弹幕是实时的，所以有两个硬指标，最初方案里"延迟不敏感、可以提前生成"的判断不成立：

- **响应延迟**：从弹幕出现到数字人开口的时间。目标先定为 3 到 5 秒以内，观众才会觉得是在回应自己。
- **持续吞吐**：在 3060 上边生成边播放，生成速度必须长期快于播放速度，否则说着说着就会断。

对应的设计：

- **流式处理，首句优先**：大模型流式输出，凑够第一句就立刻送去合成语音和口型，不等整段回复生成完。
- **待机画面兜底**：等待生成期间循环播放原视频的不说话画面，生成好一句就无缝切进去。
- **弹幕筛选与排队**：弹幕多的时候不可能条条都回，需要过滤无意义内容、合并相似问题、按优先级排队，并丢弃等待过久的弹幕。
- **固定讲解脚本可以预生成**：产品介绍这类事先写好的内容，开播前生成好语音并缓存；有弹幕时插入回复，没弹幕时播讲解。预生成只适用于这部分，不能用于弹幕回复。
- **弹幕输入做成可插拔接口**：测试用文件输入，正式用直播间实时采集。

实时采集直播间弹幕是新增的模块，原方案没有包含。抖音没有面向普通主播的公开弹幕接口，可选途径各有风险，需要单独调研后决定：

| 途径 | 优点 | 风险 |
|---|---|---|
| 读取本机直播伴侣窗口里的评论区 | 完全在本机，不碰平台协议 | 依赖直播伴侣的界面结构，版本更新可能失效，可行性待验证 |
| 连接直播间网页的弹幕通道 | 有开源实现可参考，数据完整 | 属于非官方接口，协议常变，有违反平台规则的风险 |
| 抖音开放平台的官方能力 | 合规、稳定 | 需要资质审核，普通主播很难申请 |

## 产品设计原则：普通主播就能用

目标用户是没有技术背景的主播。所有界面、流程和提示都按这个标准设计，技术细节由软件自己处理。

- **向导式开播，四步走完**：选形象（上传视频）、选声音（预置音色或克隆）、填内容（弹幕/脚本和人设）、开播。每一步只做一件事，有预览，可以随时返回修改。
- **不出现技术名词**：界面上不出现模型、显存、推理、批大小这类词。用"形象""声音""直播内容""画面流畅度"这样的说法。技术选项全部收进默认隐藏的"高级设置"。
- **自动适配电脑**：首次启动自动检测显卡和显存，选好画质、帧率和模型档位，用户不需要调任何参数。配置不够时直接说明"这台电脑的显卡不满足要求"以及最低要求是什么。
- **素材自动体检**：上传视频或音频后自动检查并用大白话反馈，例如"人脸太小，建议拍近一些""背景噪音较大，克隆的声音可能不像"。多段视频之间的切换效果给出"自然 / 一般 / 不建议"三档评级。
- **耗时操作有进度和预期**：视频预处理、声音克隆、模型下载都显示进度条和预计剩余时间，可以取消，中断后可以续传或续做。
- **开播前先试播**：在软件里预览数字人说话的实际效果，满意后再连接直播伴侣。
- **直播伴侣连接有图文引导**：一步步截图教用户在直播伴侣里添加窗口捕获和声音，并自动检测是否连接成功。
- **出错说人话并给出办法**：不显示报错代码和堆栈，只说发生了什么、该怎么办；提供"一键导出日志"方便求助。
- **内置模板**：提供带货、闲聊、知识讲解等人设和话术模板，以及示例弹幕脚本，填空即可用。
- **开播时保持稳定优先**：运行中遇到资源不足时自动降低画质或帧率保持不中断，而不是报错退出。

## 总体架构

```
弹幕/脚本 -> 调度队列 -> LLM(流式,按句切分) -> TTS(克隆音色) -> 口型驱动 -> 音画合成播放 -> 直播伴侣
                                                                      ^
                                                    人物视频(预处理后的底板帧, 无任务时循环待机)
```

进程划分：

| 进程 | 职责 | 说明 |
|---|---|---|
| 主进程 | PySide6 界面、调度、音画播放 | 不加载任何模型，保证界面不卡 |
| `llama-server.exe` | LLM 推理 | llama.cpp 官方预编译 CUDA 版，本机 HTTP 接口，与 Python 依赖隔离 |
| 推理 worker | TTS 和口型驱动 | 一个 PyTorch 进程，共用一份 CUDA 上下文以节省显存 |

进程间用 `multiprocessing` 队列传控制消息，视频帧走共享内存。

## 选型

| 环节 | 选型 | 理由 | 备选 |
|---|---|---|---|
| LLM | Qwen3-4B Q4_K_M (GGUF)，llama.cpp CUDA 版 | 中文好，约 3G 显存，短回复足够；GGUF 可按层卸载到 CPU | 显存不够时降到 Qwen3-1.7B 或部分层放 CPU |
| 声音克隆 TTS | GPT-SoVITS v2Pro | 显存约 2G，速度远快于实时；几秒参考音频即可零样本克隆，也可用 1 分钟音频微调提升相似度；MIT 许可；Windows 支持成熟 | CosyVoice2-0.5B（零样本效果好，但显存和延迟更高，Windows 安装更麻烦） |
| 口型驱动 | MuseTalk 1.5，fp16 | 专为实时设计，口型清晰度明显好于 Wav2Lip；约 4G 显存；MIT 许可 | Wav2Lip 系（更快但模糊，且许可限制商用） |
| 界面 | PySide6 | 与模型同为 Python，单一技术栈，打包简单；LGPL 可商用 | 无 |
| 音视频 | PyAV / ffmpeg 解码，`sounddevice` 播放音频 | 以音频时钟为基准对齐画面 | 无 |
| 运行环境 | Python 3.10，PyTorch 2.x + CUDA 12.x | 三个模型项目兼容性最好的组合 | 无 |

具体小版本在 PoC 阶段按各项目当时的最新稳定版锁定。

## 音色：克隆与预置共用一个引擎

GPT-SoVITS 里一个"音色"就是一段参考音频加对应文本，可选再加一份微调权重。克隆音色和预置音色因此是同一种数据，只是来源不同，不需要第二个 TTS 模型，显存预算不变。

- **音色库**：每个音色存为一个目录（参考音频、参考文本、可选微调权重、元信息），界面里统一列表选择、试听。
- **预置音色**：随安装包附带若干男女声音色。参考音频必须来源可商用（自录或已授权的开源语料），这一项需要在打包前落实。
- **克隆音色，零样本**：从人物视频自动抽取音轨，或用户上传 5 到 10 秒干净人声；用 ffmpeg 抽音轨，本地语音识别（faster-whisper，CPU 运行，不占显存）自动生成参考文本，用户可修改。
- **克隆音色，微调（可选增强）**：提供约 1 分钟音频时可在本机微调，相似度更高。微调时需要暂停直播链路以腾出显存，放在界面的"素材准备"环节，不在开播时进行。

## 多视频与平滑切换

支持为一个数字人上传多段人物视频，运行中在视频之间切换，要求画面没有突变。做法是把切换的计算全部放到导入阶段，运行时只播放缓存好的过渡帧，不增加开播时的显存和算力。

导入时（离线，一次性）：

- **规格统一**：ffmpeg 把所有视频转成相同分辨率、帧率、色彩空间。
- **逐帧姿态特征**：复用口型预处理已算出的人脸框和关键点，记录每帧的头部位置、朝向、嘴部开合。
- **找最佳切换点**：对每一对视频 A、B，搜索姿态最接近且嘴部闭合的帧对 (A 的第 i 帧, B 的第 j 帧)，作为 A 到 B 的切换点。每段视频自身的循环接缝用同样方法处理，避免循环回头时跳变。
- **生成过渡帧**：用插帧模型 RIFE 在两帧之间生成 8 到 12 帧（约 0.3 到 0.5 秒）的过渡并缓存。RIFE 只在导入阶段运行，MIT 许可。
- **差异评估**：若两段视频场景、服装、机位差别过大，插帧会产生形变，此时自动改用交叉淡化，并在界面上提示该组合的过渡质量等级。

运行时：

- 切换只发生在句子之间的停顿处，不打断正在说的话；过渡帧保持原视频口型，不做口型生成。
- 调度器收到切换请求后，继续播放当前视频到最近的切换点，播过渡帧，再从目标视频的对应帧继续。
- 切换触发方式：按时间间隔轮换或随机、在脚本里为某条内容指定视频、界面上手动切换。

效果边界需要事先说明：同一场景、同一机位、同一服装拍摄的多段视频可以做到基本无感；跨场景或换装的视频只能做到柔和过渡，做不到无感。建议用户按前一种方式准备素材。

## 送入直播伴侣的方式

直播伴侣不接收外部推流，只能添加本机素材。采用两种输出方式，默认用第一种：

1. **窗口捕获加系统声音（默认）**：应用开一个无边框播放窗口，直播伴侣用"窗口捕获"抓画面，声音走系统默认输出，由直播伴侣的桌面音频采集。不需要安装任何驱动，最适合一键安装。
2. **虚拟摄像头加虚拟声卡（可选）**：`pyvirtualcam` 输出画面，VB-CABLE 输出声音。画面更干净、不怕窗口被遮挡，但需要用户额外装两个驱动。

## 3060 12G 显存预算

| 占用方 | 预估 |
|---|---|
| 系统桌面、直播伴侣编码 | 1.0 - 1.5 G |
| MuseTalk fp16 | 3.5 - 4 G |
| GPT-SoVITS | 2 - 2.5 G |
| Qwen3-4B Q4_K_M，4k 上下文 | 约 3.2 G |
| 合计 | 约 10 - 11 G |

余量不大，需要这些措施：

- 人物视频一次性预处理：人脸检测、裁剪、VAE 潜变量、融合遮罩全部离线算好并缓存，运行时只跑 UNet 和 VAE 解码。
- 按句流水：LLM 出一句，TTS 合成一句，口型生成一句，进缓冲队列后播放；队列空时循环播放原视频待机，切换点对齐到帧。
- 三个模型不同时满载：LLM 生成很短，可以在口型生成间隙调度。
- 降级开关：LLM 层数卸载到 CPU、输出帧率 25 降到 20、口型批大小可调。

开发机是 3080 Ti，显存同为 12G，但算力约为 3060 的 1.7 倍。因此开发机上的验收线要按比例抬高：口型生成吞吐需达到约 45 fps，才能推断 3060 上稳定 25 fps。最终仍需在真实 3060 上验证一次。

## 实测数据（2026-11-25，开发机 RTX 3080 Ti 12G）

以下数据来自 `scripts/` 下的基准脚本。3060 的算力约为 3080 Ti 的 0.6 倍，表中的 3060 数值是按比例折算的估计，尚未实机验证。

单模块：

| 模块 | 实测 | 折算到 3060 | 显存 |
|---|---|---|---|
| 大模型 Qwen3-4B，llama.cpp CUDA 版 | 192 词元/秒 | 约 110 词元/秒 | 进程占用约 3.3G |
| 语音合成 GPT-SoVITS v2ProPlus | 耗时为音频时长的 0.42 倍 | 约 0.5 到 0.7 倍 | 进程占用约 3.2G |
| 口型驱动 MuseTalk 1.5，批大小 8 | 显卡部分 23 ms/帧，约 43 fps | 约 25 fps | 进程占用约 5G |

口型驱动每帧耗时拆分：UNet 7.2 ms，VAE 解码 15.8 ms，贴回原图 7.5 ms（重写后，官方实现为 25 ms，输出逐像素一致）。贴图在 CPU 上，可与显卡并行。

三模型并发（语音和口型持续满载，大模型每 3 秒回答一次）：

| 项目 | 结果 |
|---|---|
| 口型驱动 | 显卡部分 25 ms/帧，约 40 fps，与单独运行基本一致 |
| 语音合成 | 0.45 倍，与单独运行基本一致 |
| 大模型 | 109 词元/秒，单次回复平均 0.19 秒 |
| 显存峰值 | 约 12.0G，已触及显存上限 |

结论：

- **三个模型可以同时运行，互相抢占不明显**。语音合成主要受 CPU 单核速度限制，不怎么和口型抢显卡。
- **显存是当前最大的问题**。实际占用比方案最初估计的高约 1.5G，12G 的卡上没有余量，溢出后会严重卡顿（测试中出现过一句话合成 200 秒）。必须压缩：限制口型批大小、去掉运行时不需要的模型部件、缩小大模型上下文，必要时把大模型放到 CPU 上。
- **口型在 3060 上的帧率压线**，需要给 VAE 解码加速。已验证新版 PyTorch 配合 `torch.compile` 可把 VAE 解码从 15.7 ms 降到 10.7 ms，同时显存占用下降约三分之一；单纯升级 PyTorch、`channels_last`、`cudnn.benchmark` 均无效。TensorRT 尚未测试。

大模型引擎的选择：CUDA 版与 Vulkan 版单独运行时速度相近（192 对 184 词元/秒），并发时 CUDA 版更快（109 对 86）。Vulkan 版只在体积上有优势（37 MB 对 715 MB）。正式版采用 CUDA 版。

## 打包与分发

- 采用"整合包"方式：内嵌独立 Python 环境和全部依赖，加一个启动器 exe，用 Inno Setup 做安装程序。不用 PyInstaller 打包 PyTorch，那样体积大且容易出错。
- 模型权重约 10G，不放进安装包：首次启动从国内镜像（ModelScope）下载，同时提供离线模型包。下载完成后全程不联网。
- 启动时自检：显卡型号、显存、驱动版本，不满足时给出明确提示。

## 里程碑

1. **环境**：服务器装 Python 3.10、git、ffmpeg、PyTorch，下载三个模型。
2. **单模块 PoC 与基准**：分别测 MuseTalk 吞吐和显存、TTS 实时率和克隆相似度（GPT-SoVITS 对比 CosyVoice2）、LLM 速度；再测三者同时加载的显存峰值。这一步决定选型是否需要调整。
3. **命令行全链路**：脚本输入到播放窗口出画出声，验证音画同步和待机切换；加入多视频导入、过渡帧生成和运行时切换。
4. **桌面界面**：按四步向导实现，包括素材导入与自动体检、音色库（预置音色选择、克隆、试听）、弹幕/脚本编辑与模板、试播预览、开播控制、直播伴侣连接引导。
5. **直播伴侣联调**：窗口捕获和声音采集，长时间稳定性。
6. **打包**：安装程序、首启模型下载、3060 实机验证。

## 风险

- **MuseTalk 预处理依赖 mmpose/mmcv**，在 Windows 上安装麻烦。只在素材预处理时用到，PoC 时若装不顺，换成 insightface 或 mediapipe 做人脸关键点。
- **依赖冲突（已确认）**：MuseTalk 锁定 `transformers==4.39.2` 和 torch 2.0.1，GPT-SoVITS 要求 `transformers>=4.51` 和新版 torch，无法共用环境。现已拆成两个环境、两个推理进程，代价是安装包多几个 G，显存多占一份 CUDA 上下文（约 0.3 到 0.5G）。打包阶段再评估能否把 MuseTalk 升级到新版依赖后合并。
- **MuseTalk 权重的商用限制**：代码和模型以 MIT 发布，但官方 NOTICE 注明权重训练用到了 HDTF 数据集，商用问题需与 HDTF 数据集所有方沟通。若本项目要商用，需要先确认这一点，或改用可商用数据训练的口型模型。
- **开发机磁盘只剩 65G**：模型加环境加打包产物会比较紧，可能需要加挂数据盘。
- **服务器是远程桌面环境**：没有物理声卡和显示器，直播伴侣的声音采集和窗口捕获在 RDP 会话下的表现需要实测。
- **平台合规**：抖音要求数字人直播做 AI 生成内容标识，使用真人形象和声音需要本人授权。

## 验证方式

- 基准脚本 `scripts/benchmark.py`：输出各模型的显存峰值、MuseTalk fps、TTS 实时率、LLM 每秒 token 数，以及三模型并发时的总显存。验收线：总显存不超过 10.5G，口型吞吐在 3080 Ti 上不低于 45 fps。
- 全链路测试：喂入一份 20 条的弹幕脚本，检查每条都有回复播出、音画偏差不超过 80 毫秒、待机与说话切换无跳帧。
- 视频切换：导入 3 段同场景视频，循环触发全部 6 种切换和各自的循环接缝，录屏逐帧检查无跳变、无闪烁；再用一组跨场景视频确认自动降级为交叉淡化并有提示。
- 稳定性：连续运行 2 小时，显存和内存无持续增长。
- 实机：在直播伴侣里添加窗口捕获，用抖音的非公开测试直播确认观众端画面和声音正常；最后在真实 3060 12G 机器上重复以上测试。
